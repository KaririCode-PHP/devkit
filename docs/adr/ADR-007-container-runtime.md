# ADR-007: Container Runtime Generated into `.kcode/docker/`

**Status:** Accepted
**Date:** 2026-11-25
**Deciders:** Walmir Silva
**Context:** KaririCode Framework Devkit v1.2.0

## Context

Components created from the 2024 template carry their own container setup:

```
component/
├── .docker/php/Dockerfile          # php:8.3-alpine + xdebug, redis, memcached
├── .docker/php/kariricode-php.ini
├── .env.example                    # KARIRI_APP_ENV, KARIRI_PHP_VERSION, KARIRI_PHP_PORT
├── docker-compose.yml              # one "php" service, container_name per component
└── Makefile                        # ~170 lines wrapping docker-compose exec
```

The five files are copied from one template and drift: PHP versions, extensions and Makefile targets differ between components, and the Dockerfile still targets PHP 8.3 while the ecosystem requires 8.4. Every change means one pull request per component.

## Decision

The container is generated by kcode, like every other tool config:

```
.kcode/docker/
├── Dockerfile      # php:<version>-cli-alpine + install-php-extensions + Composer 2 + git
├── php.ini         # bind-mounted; Xdebug installed but off
└── compose.yaml    # "php" service plus optional sidecars
```

Settings live in `devkit.php` → `docker` (`php_version`, `image`, `extensions`, `packages`, `ini`, `environment`, `ports`, `services`, `service`, `enabled`).

Commands replace the Makefile targets:

| Legacy | kcode |
|---|---|
| `make up` / `make down` | `kcode up [--build]` / `kcode down [--volumes]` |
| `make shell` | `kcode shell [shell]` |
| `make composer-install` | `kcode exec composer install` |
| `make logs` | `kcode logs [--follow]` |
| `make test`, `make cs-check`, … | `kcode test --docker`, `kcode cs:fix --check --docker`, … |

### Key properties

1. **Same-path bind mount.** The project is mounted at its host path (`/home/dev/validator:/home/dev/validator`) and used as `working_dir`. Every absolute path kcode computes — configs, `.kcode/vendor/bin/`, build output — is valid inside the container, so `--docker` only prefixes commands with `docker compose exec`; no path translation exists.
2. **Idle service, exec per command.** The `php` service runs `sleep infinity` under `init`. Tools run through `docker compose exec -T --user <uid>:<gid> --workdir <root> php …`, so files written to the bind mount keep the developer's ownership. HOME and Composer state live in `/tmp`, so any UID works.
3. **Shared, hash-tagged image.** The built image is tagged `kcode-php:<php>-<sha1(Dockerfile)[0..12]>` with `pull_policy: missing`. Components with identical settings share one image; a settings change produces a new tag and exactly one rebuild. `php.ini` is mounted, not baked, so INI changes never rebuild.
4. **On demand.** `--docker` (or `KCODE_DOCKER=1`, or `docker.enabled`) starts the container when `docker compose ps` reports it stopped. Composer installs run inside the container too, so platform checks match the PHP that runs the tools.
5. **Xdebug per run.** `XDEBUG_MODE`, `XDEBUG_CONFIG` and `XDEBUG_SESSION` are forwarded to each exec; nothing else from the host environment is.

## Alternatives Considered

- **Keep per-component Docker files, generated once by `kcode init`.** Still five committed files per component and still drift after the first edit.
- **`docker run --rm` per command.** No `kcode up`, but a container start per tool call (about a second each) and no place for sidecar services.
- **Translate paths (`/app` inside, host path outside).** Requires rewriting every generated config and argument; the same-path mount removes the problem.
- **Use `kariricode/php-api-stack` as the default image.** It is an nginx + PHP-FPM + Redis application image. A library component needs PHP CLI, PCOV and Composer. It stays available through `docker.image`.

## Consequences

### Positive

- Components lose `.docker/`, `docker-compose.yml`, `.env.example` and the Docker Makefile (`kcode migrate` removes them).
- One definition for the whole ecosystem; updating the PHP version or an extension is a devkit release, not 35 pull requests.
- The host needs Docker and PHP 8.4 for kcode itself; tool versions, extensions and services come from the container.

### Negative

- The same-path mount requires a POSIX project path (Linux, macOS, WSL2). Native Windows paths such as `C:\…` are not supported.
- The first `kcode up` builds the image (needs network for the base images, PECL and Alpine packages).
- `docker.image` must provide `php` and `composer` on `PATH`; kcode cannot verify a prebuilt image beyond the coverage-driver probe.
